Composing Salesforce: The Assembly Pattern

How to compose modular Salesforce orgs from disparate parts — without the monster turning on you.

Every enterprise Salesforce org eventually looks the same underneath: a core of business logic wrapped in layers of integrations, each added by a different team, at a different time, for a reason nobody fully wrote down. The Assembly Pattern is a way of naming that reality on purpose — instead of pretending your org is one clean system, you design it as a set of clearly bounded modules that are stitched together deliberately.

Why "composed" beats "monolithic"

A monolithic org treats every trigger, flow, and integration as part of one undifferentiated blob. When something breaks, you're debugging the whole organism. A composed org draws boundaries around functional areas — billing, fulfillment, support — so a change in one module has a predictable blast radius.

You can't stop teams from bolting new pieces onto the org. You can control how those pieces attach.

The three seams every module needs

  • A data contract — which objects and fields this module owns, and which it only reads.
  • An entry point — one invocable method, platform event, or flow that other modules call, instead of reaching into internals.
  • An owner — a team or person who can approve changes to that module's seam.

Retrofitting an existing monster

You rarely get to build this way from day one. More often, you're carving seams into an org that already exists. Start by mapping which automations touch which objects, group the tangled ones into a module, and give that module a single validated entry point going forward — even if the internals stay messy for now. The goal isn't a rewrite. It's making the next change safer than the last one.

Do this consistently and the org stops being one organism you're afraid to touch, and starts being a set of parts you can reason about individually — which is, really, the whole point of an assembly.
